# Доменная маршрутизация для OpenWrt 25+

Проект направляет выбранные домены через TUN-интерфейс **sing-box**. Требуется
OpenWrt 25 или новее. Старые выпуски OpenWrt, а также
WireGuard, AmneziaWG, OpenVPN и tun2socks больше не поддерживаются.

## Что изменилось в OpenWrt 25

В OpenWrt 25 пакетный менеджер `opkg` заменён на **`apk`**. Поэтому установщик
использует `apk update` и `apk add`. Проект теперь рассчитан только на firewall4/nftables
и списки dnsmasq `nfset`; код совместимости со старым ipset удалён.

Команда запуска загружает скрипт через входящий в BusyBox `wget`. Автономный
установщик до внесения изменений проверяет версию OpenWrt и наличие `apk`. Он
устанавливает `curl`, `sing-box`, `dnsmasq-full`, `ip-full` и `nano`,
создаёт правила для `tun0`, сохраняет команды диагностики и удаления в
`/usr/bin` и не перезаписывает существующий `/etc/sing-box/config.json`. В конце
установки скрипт предлагает сразу открыть этот конфиг в `nano`, проверяет его и,
если конфигурация корректна, перезапускает sing-box после применения настроек
сети.

Поддерживается только автономный установщик; Ansible-роль удалена.

## Установка

```sh
wget -O /tmp/getdomains-install.sh https://raw.githubusercontent.com/overm/domain-routing-openwrt/master/getdomains-install.sh && sh /tmp/getdomains-install.sh
```

Для установки из другой ветки или конкретного коммита задайте один источник
для установщика и всех вспомогательных файлов. Замените `BRANCH_OR_COMMIT`
именем ветки или полным SHA коммита:

```sh
getdomains_ref='BRANCH_OR_COMMIT'
getdomains_source="https://raw.githubusercontent.com/overm/domain-routing-openwrt/$getdomains_ref"
wget -O /tmp/getdomains-install.sh "$getdomains_source/getdomains-install.sh" && \
GETDOMAINS_SCRIPT_BASE_URL="$getdomains_source" sh /tmp/getdomains-install.sh
```

Дополнительные флаги, например `--wdns`, добавляются после имени скрипта.
Без `GETDOMAINS_SCRIPT_BASE_URL` вспомогательные файлы загружаются из `master`,
даже если сам установщик скачан из другой ветки. Для повторного запуска из
`/tmp` также передавайте эту переменную. Полный SHA фиксирует одну версию всех
файлов; содержимое ветки может измениться между загрузками.

Во время установки выберите один доменный список: **Russia inside** (по
умолчанию), **Russia outside** или **Ukraine**.

Без дополнительных флагов IPv4 выбранных доменов идёт через туннель, но при
исчезновении маршрута через `tun0` может продолжить путь напрямую. IPv6 не
маршрутизируется в туннель и также разрешён напрямую. Это режим fail-open.

### Дополнительные параметры

#### `--no-icanhazip`

По умолчанию установщик добавляет `icanhazip.com` в набор `vpn_domains`, чтобы
проверка внешнего IPv4 выполнялась через туннель. Правило
`mark_local_domains` маркирует совпадающий трафик самого роутера в
`mangle_output`, поэтому для однозначной проверки используйте
`curl -4 icanhazip.com`. Без `-4` curl может выбрать разрешённый напрямую IPv6.
При включённом `--ipv6-deny` домен добавляется также в `vpn_domains6`. Эта
привязка сохраняется как
отдельная секция `vpn_icanhazip` в `/etc/config/dhcp` и отображается в LuCI на
вкладке **DNS → IP Sets**; в загружаемый файл `/tmp/dnsmasq.d/domains.lst`
установщик её не дописывает. Чтобы развернуть конфигурацию без этого домена,
запустите установщик с флагом `--no-icanhazip`:

```sh
sh /tmp/getdomains-install.sh --no-icanhazip
```

#### `--ipv6-deny`

По умолчанию ответы AAAA для выбранных доменов разрешены напрямую через IPv6.
Флаг `--ipv6-deny` создаёт набор `vpn_domains6`; dnsmasq помещает в него AAAA,
а firewall отклоняет новые совпадающие соединения из LAN и от самого роутера.
`REJECT` возвращает ошибку сразу, поэтому клиент с поддержкой IPv4 обычно может
быстро попробовать адрес A. Если у домена нет рабочего IPv4, соединение не
будет установлено:

```sh
sh /tmp/getdomains-install.sh --ipv6-deny
```

#### `--kill-switch`

По умолчанию отсутствие маршрута в таблице `vpn` не останавливает обработку
policy rules, и маркированный IPv4 может уйти через основной маршрут. Флаг
`--kill-switch` добавляет следующее правило `unreachable` для mark `0x1`:
сначала правило с приоритетом 100 ищет маршрут в таблице `vpn`, затем правило с
приоритетом 110 запрещает прямой IPv4, если маршрут не найден.

```sh
sh /tmp/getdomains-install.sh --kill-switch
```

Это не healthcheck. Если `tun0` и маршрут существуют, но удалённый прокси не
отвечает, трафик может зависнуть в туннеле; автоматического переключения или
блокировки по состоянию прокси нет. Сам по себе `--kill-switch` не запрещает
IPv6. Для запрета обоих прямых путей используйте флаги вместе:

```sh
sh /tmp/getdomains-install.sh --kill-switch --ipv6-deny
```

| Параметры | IPv4 при отсутствии маршрута `vpn` | IPv6 выбранных доменов |
| --- | --- | --- |
| без флагов | напрямую | напрямую |
| `--kill-switch` | запрещён | напрямую |
| `--ipv6-deny` | напрямую | запрещён |
| оба флага | запрещён | запрещён |

Повторный запуск установщика применяет указанный режим: отсутствие
`--kill-switch` или `--ipv6-deny` удаляет ранее созданные правила именно этой
опции. Сохраняемые секции обновляются на месте: запуск с теми же параметрами
не меняет их порядок в конфигурации.

#### `--wdns`

Флаг `--wdns DNS_IPV4` создаёт DHCP-тег `wdns`, задаёт для него DNS-сервер и
добавляет приоритетное правило маршрутизации указанного IPv4-адреса через
таблицу `vpn` (туннель). Например:

```sh
sh /tmp/getdomains-install.sh --wdns 172.16.250.2
```

При обновлении повторный запуск установщика без `--wdns` сохраняет существующий
DHCP-тег `wdns` и создаёт или исправляет соответствующее правило маршрутизации.

Тег `wdns` — дополнительная возможность для гибкой настройки клиентов. Его
целесообразно использовать, когда весь трафик клиента уже направлен через
туннель: клиент обращается к указанному DNS напрямую, поэтому его запросы не
обрабатывает локальный dnsmasq, записи DNS из LuCI не применяются, а доменные
nft-наборы не пополняются по этим запросам. Сам тег не направляет весь трафик
клиента через туннель; он меняет только выдаваемый DNS-сервер. Для работы
локальных записей и маршрутизации по доменным спискам клиент должен использовать
DNS роутера.

Чтобы клиент со статической арендой получил этот DNS вместе с фиксированным
IPv4-адресом, добавьте тег к соответствующей секции `host` в
`/etc/config/dhcp` (или выберите тег `wdns` для static lease в LuCI):

```text
list tag 'wdns'
```

При удалении установки правило маршрутизации DNS-сервера удаляется вместе с
DHCP-тегом `wdns`.

## Раздельный DNS и LuCI

При `--wdns DNS_IPV4` или сохранённом теге `wdns` клиенты с DNS роутера разрешают
домены списка через WDNS. Сервис автоматически создаёт `server=/domain/DNS_IPV4`
для скачанного списка и ручных записей **DNS → IP Sets**, содержащих
`inet/fw4/vpn_domains` или `vpn_domains6`. Остальные запросы идут к DNS WAN из
`/tmp/resolv.conf.d/resolv.conf.auto`; без WDNS все запросы используют DNS WAN.
Для DNS провайдера включите их получение на WAN: вручную заданные DNS WAN
заменяют адреса провайдера в этом файле.

Установщик включает этот resolv-файл и отказывается продолжать при глобальных
DNS-перенаправлениях, нарушающих выбор DNS. Перенаправления конкретных доменов,
локальные зоны, адреса и локальные имена остаются под управлением LuCI и имеют
приоритет над автоматически создаваемыми DNS-правилами. При таймауте WDNS
повторного запроса выбранного имени через DNS провайдера нет. Для адреса WDNS
действует поиск в таблице VPN с приоритетом 80 и отдельное правило `unreachable`
с приоритетом 81: оно запрещает прямой резервный маршрут даже без `--kill-switch`.
Временные запреты с приоритетом 79 защищают старый и новый адрес WDNS при смене
сервера и загрузке, пока сетевые правила и конфигурация DNS не будут готовы.

Ручная запись IP Sets управляет своим доменом и поддоменами; более конкретная
ручная запись перекрывает родительскую. Строки с одинаковым доменом объединяются
в одно эффективное nftset-правило со всеми их наборами; исходные записи UCI
сохраняются. Запись только с посторонними наборами использует обычный DNS, не
наследуя WDNS от автоматического родителя. Учитывается порядок OpenWrt 25:
confdir читается раньше nftset-правил UCI; стендовые тесты проверяют этот порядок.
Наборы должны существовать. Используйте обычные DNS-имена, для IDN — punycode,
и правильный экземпляр dnsmasq. Установщик управляет первым экземпляром; записи
с явной привязкой к другому экземпляру остаются в управлении этого экземпляра.

Локальные записи `domain`/`hostrecord`, сопоставления `address` и цепочки локальных
CNAME продолжают разрешаться локально. Их выбранные адреса добавляются в наборы проекта:
обработка внешнего ответа dnsmasq не вызывается для локальных ответов.
Посторонними наборами управляет их собственный сервис. Динамические DHCP-имена
и произвольные дополнительные hosts-файлы для добавления IP не перечисляются;
их DNS-ответы работают. Для гарантированной маршрутизации добавьте локальные записи имён
или статические IP в firewall.

Save & Apply запускает генерацию; монитор с интервалом две секунды также
отслеживает изменения и удаления. LuCI и генератор работают отдельно: при
совпадении по времени старая конфигурация может кратковременно оставаться
активной. Изменившийся снимок отбрасывается и проверяется повторно; после
публикации нового файла сервис перезапускает dnsmasq. После завершения Apply
запустите `getdomains-check`: он сравнивает рабочие правила с UCI и сохранённым
списком. Не редактируйте `domains.lst` вручную. Посторонние файлы confdir и ручные
записи LuCI сохраняются при удалении. Фильтры расширений confdir не поддерживаются.
Перезапуск dnsmasq очищает DNS-кеш и может прервать текущие DNS-запросы и DNS-сессии
по TCP; обычно клиент повторяет запрос. Действующие соединения приложений
сохраняют своё решение о маршруте.

Решение о маршруте IPv4 сохраняется в conntrack для VPN и прямых соединений.
Добавление или удаление IP, истечение timeout и изменение DNS-правил не меняют
решение действующего отслеживаемого соединения. Новые соединения используют
текущее содержимое наборов. Марка маршрута восстанавливается только для исходного
направления, поэтому ответы не отправляются обратно в туннель. Зарезервированы
биты `0x1` для маршрута и `0x40000000` для классификации; остальные сохраняются.
Не назначайте эти биты другому сервису политик. Установщик отключает программный
и аппаратный flow offloading, обходящий обработчики. При удалении исходные
параметры DNS/offloading восстанавливаются, если они всё ещё имеют установленные
проектом значения. Установка, авария туннеля, очистка conntrack и ручное изменение
маршрутов по-прежнему могут прервать соединения.

## Типичные сценарии в LuCI

Все действия ниже выполняются через веб-интерфейс LuCI. Сначала закрепите за
клиентом IPv4-адрес: откройте **Network → DHCP and DNS → Static Leases**,
добавьте или отредактируйте аренду по MAC-адресу клиента и нажмите **Save &
Apply**. В примерах используется адрес `192.168.25.139`; замените его адресом
своего клиента.

### Весь IPv4-трафик клиента через туннель

1. Откройте **Network → Routing → IPv4 Rules** и нажмите **Add**.
2. Укажите исходную сеть (Source) `192.168.25.139/32`. Остальные условия оставьте
   пустыми.
3. На вкладке **Advanced Settings** выберите таблицу `vpn`, сохраните правило и
   нажмите **Save & Apply**.

Не редактируйте существующее правило **Routing** с приоритетом `100`: оно
обслуживает доменную маршрутизацию по метке `0x1`. Приоритет `70` выполняет
новое правило клиента раньше служебных правил проекта с приоритетами `80`, `90`
и `100`.

Туннель проекта обслуживает только IPv4. IPv6 клиента по-прежнему идёт напрямую,
если он отдельно не отключён в настройках сети. Если маршрут в таблице `vpn`
исчезнет, поиск продолжится по следующим правилам и IPv4 клиента сможет перейти
на прямой маршрут. Чтобы запретить такой fallback, добавьте ещё одно правило
**IPv4 Rules** с приоритетом `71`, типом **unreachable** и тем же источником
`192.168.25.139/32`; таблицу для него не указывайте. Общий kill switch проекта
проверяет метку `0x1` и сам по себе не защищает это source-based правило.

Перед запуском `getdomains-uninstall` удалите вручную созданное правило в разделе
**Network → Routing → IPv4 Rules** и нажмите **Save & Apply**. Скрипт удаления
удаляет только собственные именованные правила проекта; если оставить ручные правила,
после удаления таблицы `vpn` оно заблокирует весь IPv4-трафик этого клиента.

### DNS-сервер из туннеля для конкретного клиента

Сценарий работает, если установка настроена с опцией `--wdns DNS_IPV4`. Она
создаёт DHCP-тег `wdns` и отдельное правило, направляющее указанный DNS-сервер в
таблицу `vpn`, поэтому правило полной маршрутизации из первого сценария не
требуется.

1. Откройте **Network → DHCP and DNS → Static Leases**, отредактируйте аренду
   клиента и добавьте
   `wdns` в поле **Set Tag**.
2. Нажмите **Save & Apply**, затем переподключите клиента к сети или обновите на
   нём DHCP-аренду.

DHCP option 6 сообщает клиенту адрес DNS-сервера, но не может запретить
вручную настроенный DNS или DNS over HTTPS.

### Весь IPv4-трафик клиента только напрямую

Этот сценарий противоречит первому: для одного IP нужно выбрать только один из
них.

1. Откройте **Network → Firewall → Traffic Rules** и отредактируйте существующее
   правило `mark_domains`.
2. В поле **Source address** добавьте отрицательный адрес
   `!192.168.25.139` без суффикса `/32`.
3. Нажмите **Save & Apply**.

Такой клиент не получает метку `0x1` даже при обращении к адресам из
`vpn_domains`, поэтому его IPv4-трафик использует обычную таблицу маршрутизации
и WAN. Не добавляйте отрицательный адрес в правило **Network → Routing**:
его поле **Source** принимает только обычную CIDR-подсеть и не поддерживает `!`.

По умолчанию IPv6 уже идёт напрямую. Если установлен режим `--ipv6-deny`,
правило `block_domains6` продолжит блокировать выбранные домены для этого
клиента. Чтобы разрешить ему прямой IPv6, в том же разделе **Traffic Rules**
отредактируйте `block_domains6` и добавьте MAC-адрес клиента с `!` в поле
**Source MAC address**, например `!AA:BB:CC:DD:EE:FF`.

```sh
getdomains-check --lang=ru
```

## Удаление

```sh
getdomains-uninstall
```

Скрипт удаления убирает правила доменной маршрутизации, но намеренно сохраняет
пакет и конфигурацию sing-box. Обе команды загружаются установщиком и остаются
доступны локально после очистки каталога `/tmp`; при удалении они также удаляются.

Определение DHCP-тега `wdns` и его правила маршрутизации удаляются. Статические
DHCP-записи и указанные в них теги, включая ссылки на `wdns`, сохраняются.
После удаления эти ссылки не задают DNS-сервер; повторная установка с
`--wdns DNS_IPV4` восстановит определение тега для сохранённых записей.

## Конфигурация sing-box

Если `/etc/sing-box/config.json` отсутствует, установщик создаст
Shadowsocks-шаблон с параметрами `CHANGE_ME`. Заполните их во время установки:
при некорректной конфигурации sing-box не будет перезапущен, а первоначальная
загрузка списка будет пропущена. Существующий конфиг не перезаписывается.

Позже отредактировать и проверить конфигурацию можно командами:

```sh
nano /etc/sing-box/config.json
sing-box check -c /etc/sing-box/config.json
service sing-box restart
```

Ниже приведён отдельный базовый пример, который использует основное подключение
роутера в качестве выхода (`outbound`). Это не шаблон, создаваемый установщиком.
Пример можно взять за основу и изменить блок `outbounds` под свою конфигурацию.

```json
{
  "log": {
    "level": "warning"
  },
  "inbounds": [
    {
      "type": "tun",
      "tag": "tun-in",
      "interface_name": "tun0",
      "address": [
        "172.16.250.1/30"
      ],
      "auto_route": false,
      "stack": "system"
    }
  ],
  "outbounds": [
    {
      "type": "direct",
      "tag": "direct-out"
    }
  ],
  "route": {
    "auto_detect_interface": true,
    "final": "direct-out"
  }
}
```

Для TUN-конфигурации оставьте `route.auto_detect_interface: true` либо задайте
эквивалентный глобальный `route.default_interface`. Вариант с
`outbound.bind_interface` безопасен, только если привязан каждый outbound,
который может быть выбран для TUN-трафика; диагностика консервативно требует
привязку у всех outbound. Без одного из этих механизмов трафик может вернуться
в `tun0` и образовать петлю. Эту настройку нужно проверить и в собственном
конфиге.


## Обновление списков

Обновление списков выполняется транзакционно: данные сначала загружаются во
временный файл, проверяются ограничение размера, ожидаемый формат и синтаксис
dnsmasq, и только после успешной проверки активный файл атомарно заменяется.
Для `--ipv6-deny` при обработке к каждой записи добавляется набор
`vpn_domains6`. Блокировка исключает одновременный запуск из cron и вручную,
при ошибке сети или проверки продолжает работать предыдущий список, а dnsmasq
перезапускается только при изменении эффективных DNS-правил. Firewall и conntrack
не очищаются. Обновление запускается
ежедневно в 04:00 и загружает список через `tun0`.

`vpn_domains` и, при включённом `--ipv6-deny`, `vpn_domains6` хранят отдельные
IP-адреса с timeout два дня и лимитом 65536 элементов. Когда новое
соединение из LAN или от самого роутера обращается к уже известному адресу,
nftables обновляет его timeout до двух дней. Проверка членства выполняется до
операции `update`, поэтому трафик к неизвестному адресу не может добавить его в
набор. Ограничение `ct state new` исключает запись в набор для каждого пакета;
неиспользуемые адреса автоматически удаляются. Одно непрерывное соединение не
продлевает timeout после своего первого пакета: для продления должно начаться
новое соединение к тому же адресу.

Последний проверенный список сохраняется в `/etc/getdomains/domains.source` и
обрабатывается до запуска dnsmasq при загрузке. Flash записывается только при
изменении исходного списка; временные файлы скачивания находятся вне confdir.
Изученные IP остаются в оперативной памяти. После перезагрузки они появляются
после DNS-запросов через локальный dnsmasq. До этого адреса из кеша клиента
могут не попасть под `--kill-switch` или `--ipv6-deny`. Общий IP CDN может
обслуживать несколько имён: добавление по домену списка влияет и на другие
домены с тем же адресом. При отсутствии маршрута VPN kill switch блокирует
такой общий IPv4, а `--ipv6-deny` отклоняет общий IPv6. Обновление timeout
выполняется по IP: новые соединения к общему CDN-адресу продлевают его присутствие,
даже если они относятся к другому домену. Поэтому популярный общий адрес способен
оставаться в наборе дольше двух дней; при `--ipv6-deny` его продлевают в том
числе повторные отклонённые попытки соединения.

Правила действуют на адреса, полученные локальным dnsmasq, и добавленные
локальные статические записи. Внешний DNS, DNS over HTTPS и обращения к IP напрямую не
создают новые элементы наборов и могут обойти доменную политику. Обращение к IP,
уже находящемуся в наборе, обновляет его timeout.

Устройство регистрируется в netifd как неуправляемый логический интерфейс
`singbox_tun`. Для локального процесса `curl`, привязанного к `tun0`, создаётся
отдельное policy rule через `singbox_tun`: поле `out` в UCI ссылается на
логический интерфейс OpenWrt, а не непосредственно на имя Linux-устройства.
TUN-зона отклоняет новый входящий трафик к роутеру и новые перенаправления из
неё. Системный TUN-стек sing-box создаёт для клиентского соединения новый TCP
поток, который conntrack ещё не считает `ESTABLISHED`. Отдельное узкое правило
принимает его только от TUN-peer `172.16.250.2` к адресу `172.16.250.1` и
стандартному диапазону локальных ephemeral-портов `32768-60999`. Порты SSH,
LuCI и DNS оно не открывает. Перед каждой загрузкой скрипт до 30 секунд ждёт
появления интерфейса и успешного разрешения имени источника, поэтому короткий
перерыв DNS при применении сетевых настроек не приводит к немедленной ошибке.
Источник списка должен быть доступен через настроенный туннель.
Перед первым обновлением настройте и запустите sing-box. Если установщик не смог
выполнить начальную загрузку, после запуска туннеля выполните
`/etc/init.d/getdomains refresh` вручную.


Удаление домена прекращает будущий выбор DNS, но изученные IP остаются до timeout:
они могут принадлежать другим именам, а новый трафик продлевает их срок жизни.
DNS TTL и timeout набора независимы; добавление существующего IP через dnsmasq
не обязательно продлевает его срок. Новое соединение к старому IP из кеша после
истечения timeout может обойти политику. Закрепление защищает действующие
соединения и не превращает доменную маршрутизацию в строгий контроль по именам.
Локальные статические записи добавляются повторно каждый час с чередованием
timeout 172799/172800 секунд, чтобы продлевать срок их адресов.
